# ADR-001：引入独立审查 Agent，并接受首字延迟上升的代价

- **状态**：已采纳
- **日期**：2026-10
- **影响范围**：`app/agents/supervisor.py`、`app/agents/verifier.py`、`/api/v1/chat`、`/api/v1/chat/stream`

## 背景

CodePilot 是一个知识库问答系统。用户会拿回答里的数字、文件名、配置项去做实际决策，
因此**答案是否有依据**比**回答多快**更重要。

改造前的实现是「Supervisor 意图分类 → Worker 生成 → 直接交付」，存在一个无法自我发现的失败模式：

> 检索为空、或工具没有返回数据时，**模型仍会给出具体答案**。
> 例如没查数据库却回答「知识库中包含 3 份文档」，而实际是 0 份。

这类错误的特征是最危险的：

- **不抛异常**，请求返回 200
- **日志正常**，没有任何 error 级别记录
- **答案通顺**，用户无法从语气判断真假
- 只有比对真实数据源才能发现是错的

根因是：同一个模型在**同一次生成**里已经沿着那条推理路径走完了，
它「认为」答案是对的，因此无法可靠地审查自己。

## 决策

引入一个独立的**审查 Agent（Verifier）**，把「生成」与「审查」拆成两次独立的 LLM 调用，
并在图上构建反馈回路：

```
worker → verifier ─通过→ finalize → 交付
              │
              └─不通过→ revise →（携带 feedback 回到原 worker，上限 3 轮）
                                    │
                                    └─超限→ 诚实拒答，绝不交付原草稿
```

具体规则：

1. Verifier 只看 **问题 + 证据 + 草稿**，不参与生成，因此不受生成路径的思维定势影响
2. 判定原则：草稿中每个具体事实都必须能在【参考资料】中找到出处；
   资料不足但**明确说明无相关信息**判定为通过（诚实拒答是合格答案）
3. 审查不通过时，`feedback` 写入 state 并注入下一轮生成的 system prompt
4. 修订回到**原来那条分支**（不重新分类），避免路由抖动
5. 连续 3 轮未通过 → 输出诚实拒答，**原草稿绝不交付**

## 后果

### 正面

| 项 | 改造前 | 改造后 |
|---|---|---|
| 「知识库里有哪些文档？」 | **回答「3 份」——编造的（实际 0 份）** | 回答「0 份」，依据工具真实返回值 |
| 执行轨迹 | 只有分类一行 | 分类 → 工具调用 → 审查结论 → 定稿，完整链路 |
| 无依据内容的交付 | 可能发生，且不可观测 | 被拦截；拒答并说明原因 |

### 负面（**必须如实说明**）

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 首字延迟 | ~1.46s | **~2.42s（+66%）** |
| 输出方式 | LLM 层 `astream` 逐 token 透传 | 定稿后分片下发（仅打字机节奏） |
| LLM 调用次数/请求 | 2（分类 + 生成） | **3（分类 + 生成 + 审查）** |
| 成本 | 基准 | 约 +50% |

**核心取舍**：为了保证审查能拦住**整段**内容，必须采用「完整生成 → 审查 → 再下发」，
因此**真正的逐 token 流式没有了**。
**全文审查与真流式在单次请求内不可兼得。**

本项目选择**可靠性优先**。若要两者兼得，可改为**分段审查**
（生成一段 → 审查一段 → 通过即下发），代价是无法发现跨段落的不一致。

### 明确的非目标

- **Verifier 不保证 100% 正确**。它同样是一次 LLM 判定，也可能误判。
  它做到的是把「无依据断言」这类高发错误拦在交付之前，并让判定结论可观测
  （写入 `agent_trace`）。
- **不解决混合意图**。当前仍是单跳路由，一次只能走一条分支。
  「列出文档并总结第一条」这类需求仍需升级为 worker 工具化或并行 Worker 才能处理。

## 备选方案与未采纳原因

| 方案 | 未采纳原因 |
|---|---|
| 加强 system prompt（「不要编造」） | 属于**请求**模型遵守，不是**保证**。已在 prompt 中写了 4 条约束，仍会编造 |
| 检索/工具结果为空时直接拒答 | 过于粗暴。有些问题资料不足但可诚实说明后部分回答；且无法拦截「资料存在但草稿超出资料」的情况 |
| 用规则校验（如检查数字是否出现在证据里） | 只能覆盖数字类断言，无法判断「结论是否被证据支持」，召回率太低 |
| 让生成模型自评（self-critique） | 同一次生成内的自评受限于已走过的推理路径，实测难以发现自身编造 |
| 分段审查以保住真流式 | 可行但无法发现跨段落不一致；作为**后续演进方向**保留，不作当前方案 |

## 验证方式

该决策的可验证性已固化在测试中：

- `verify_project.py`（38 项，不依赖 LLM）：
  - 断言图中存在 `worker → verifier → revise → worker` **回路**（结构证据）
  - 断言**审查不通过时 `finalize` 输出的必须是拒答，且原草稿内容绝不能出现在输出里**
  - 断言审查结果解析容错（Markdown 包裹、前后夹带解释文字）与失败时的 fail-open 标记
- `backend/tests/test_verifier.py`：上述逻辑的 pytest 版本
- `verify_llm_flow.py`（11 项，需真实 API Key）：
  - 「无证据却给出具体数字」→ 判不通过
  - 「有证据且一致」→ 判通过
  - 「资料不足但诚实说明」→ 判通过
  - 完整图执行的轨迹包含分类、工具调用、审查结论

延迟数据由 `measure_verifier_cost.py` 实测得出。
